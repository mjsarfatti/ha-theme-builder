Notes — every derived color was checked against its own two neighbors in the sequence (in OKLCH): the fraction each HA color sits between its neighbors along hue, and how much its lightness/chroma deviates from a straight line between them, was recomputed and re-applied per system rather than eyeballed — a few derived values shifted slightly from an earlier pass once checked this way (most visibly Chakra's indigo, which HA renders as a real local dip in lightness, not a midpoint blend). Brown and blue-grey are treated as native throughout (no dot) since every system lands close enough natively. Tailwind: HA's palette is Material Design under the hood, so most names map 1:1 (light-blue→sky, blue-grey→slate — Tailwind's own official rename of blueGray). Tailwind doesn't subdivide as finely as Material at the yellow/amber and orange/deep-orange boundaries, and in practice HA leans on amber and deep-orange far more than plain yellow/orange (better contrast on light backgrounds), so those two get the real Tailwind swatches (yellow→amber, orange→deep-orange) while yellow and orange are derived to sit correctly around them. Same logic for lime/light-green: Tailwind's lime goes to light-green, lime is derived. Bulma ships only 8 hues total (red, orange, yellow, green, turquoise, cyan, blue, purple) — everything else here is derived; $orange is used for deep-orange (same reasoning as above), with amber and orange re-derived around it. Indigo lands almost exactly on Bulma's own $blue, and HA blue lands on Bulma's $cyan. Material Accent is the accent (A100/200/400/700) column per hue family, each picked to best match the lightness/chroma of the HA 500-shade; brown and blue-grey have no true Material accent (Google never defined one), so the regular 500 is shown. Ant Design ships 12 hues (red, volcano, orange, gold, yellow, lime, green, cyan, blue, geekblue, purple, magenta) and — unlike Tailwind/Bulma — already keeps yellow/gold and orange/volcano distinct, so no swap was needed there: gold→amber and volcano→deep-orange are both direct, close hue matches. geekblue lands almost exactly on HA indigo. Chakra UI ships 10 hues (gray, red, orange, yellow, green, teal, blue, cyan, purple, pink) with no indigo, lime, gold, or volcano equivalents, so it hits the same yellow/amber and orange/deep-orange conflict as Tailwind/Bulma — resolved the same way. Chakra's neutral gray carries a slight cool/blue cast that lines up with HA's blue-grey, so that one's used directly.

Rounded Theme derives from a small 6-color custom palette (red, orange, yellow, green, blue, purple RGB triplets — each an obvious hue match to its HA slot, all within ~8–17° and sitting in a tight pastel band, L≈0.77–0.92, C≈0.10–0.13 in OKLCH). It uses the "shape-matched" method documented below.
Methodology — "shape-matched" derivation (click to expand)

Goal: given a partial palette (some of the 18 HA hues have a real/native counterpart in the target system, some don't), fill in the missing ones so that each derived color sits in the same relative position to its neighbors — in lightness and chroma — that the real HA color occupies relative to its own neighbors. Not a plain color blend: a blend imports only hue and position; this imports HA's actual local shape (a dip, a bump, a sharp desaturation) and reproduces it proportionally, however vivid or muted the target system's own colors happen to be.

0. Fixed reference: the 18-color sequence. All reasoning happens along one fixed order, which follows the hue wheel from HA's own values:

red, pink, purple, deep-purple, indigo, blue, light-blue, cyan, teal, green, light-green, lime, yellow, amber, orange, deep-orange, brown, blue-grey

Index 0 = red … index 17 = blue-grey. Every "neighbor" reference below means adjacent indices in this exact list.

1. Convert everything to OKLCH. Take the HA hex for all 18 colors, and the target system's hex for whichever ones are native/real, and convert each to OKLCH (L 0–1, C, H in degrees). Standard sRGB → linear → OKLab → OKLCH pipeline (Björn Ottosson's reference formulas).

2. Unwrap HA's hue sequence. Hue is circular (0–360°) but the 18-color sequence moves steadily in one direction around the wheel (decreasing, in HA's case), crossing the 0°/360° boundary once between pink and purple. Before doing any arithmetic, unwrap it into a continuously decreasing (or increasing) number line, e.g.:

red 28.8, pink 9.6, purple 302.0→−58.0, deep-purple 299.8→−60.2, indigo 271.4→−88.6, … deep-orange 43.8→−316.2

Without this step, hue-fraction math silently breaks for any pair straddling the wrap.

3. Mark native cells, process the rest left to right. Cells with a real target-system value are "native" from the start. Go through the derived (missing) indices in order, index by index. Once a derived cell is computed, immediately mark it native too — later cells are allowed to reference it as a solid anchor. This matters: it's why the process is order-dependent and must run left→right, not all at once.

4. Choose the reference pair (a, b) for index i:

  • Default: a = i−1, b = i+1 — interpolate between the immediate previous and next colors.
  • If i+1 is not yet native (still waiting to be derived) — i.e. two derived cells sit back to back — shift the whole window back: a = i−2, b = i−1 instead. This avoids referencing an unreliable/not-yet-computed neighbor.
  • Edge case: if i is the last index in the sequence (no i+1 exists at all, e.g. blue-grey), always use a = i−2, b = i−1.

5. Compute the hue fraction t, from HA only:

t = (Hu[i] − Hu[a]) / (Hu[b] − Hu[a])

using the unwrapped HA hues from step 2. Note t is not clamped to [0,1] — when the reference pair was shifted back per step 4, t will legitimately be >1 (extrapolation beyond b, in the direction away from a). This is expected and fine for hue; see the caveat at the end for why it can misbehave for chroma in extreme cases.

6. Compute HA's own predicted vs. actual L and C at that t — this is the "shape":

pred_L = HA_L[a] + t·(HA_L[b] − HA_L[a]) pred_C = HA_C[a] + t·(HA_C[b] − HA_C[a]) r_L = HA_L[i] / pred_L (how much brighter/darker the real HA color is vs. a straight line between its neighbors) r_C = HA_C[i] / pred_C (same, for saturation)

7. Apply the same t and the same ratios to the target system:

target_pred_L = target_L[a] + t·(target_L[b] − target_L[a]) target_pred_C = target_C[a] + t·(target_C[b] − target_C[a]) target_L[i] = target_pred_L · r_L target_C[i] = target_pred_C · r_C target_H[i] = HA_H[i] (hue is always taken directly from HA, unchanged — never interpolated)

8. Convert back to hex (OKLCH → OKLab → linear sRGB → sRGB, clamped to [0,1] per channel) and store; mark the cell native; move to the next derived index.

Why ratios, not absolute deltas: multiplying by r_L/r_C scales proportionally to whatever range the target system actually uses, so it works whether the target's colors are pale pastels or saturated brand colors — a steep HA drop (e.g. brown/blue-grey collapsing to near-zero chroma) reproduces as a steep drop in the target too, even if every target anchor is a vivid, high-chroma color. A plain linear blend (no ratio) doesn't have this property, which is why it was dropped as a method — it flattens exactly the contrasts this process exists to preserve, and can extrapolate to implausible results at sequence boundaries with nothing to correct it.

Caveat: when the reference pair requires heavy extrapolation (t far outside [0,1] — most likely at the very start/end of the sequence, or several back-to-back derived cells in a row) chroma in particular can occasionally overshoot. If a result looks visibly off, the fix used elsewhere in this table was to re-derive that one cell using the true (not shifted-back) real neighbors once they exist, or to interpolate directly from the nearest real anchors on both sides rather than chaining through several derived cells in sequence.
